## 二、核心原则（红线）

- `main` 是唯一开发基线
- 新功能必须在 `feature/*` 分支开发
- Bug 修复在 `hotfix/*` 分支修复
- 一个 AI 线程只处理一类任务
- 线程结束必须输出交接摘要
- 代码变更涉及接口/数据结构 → 同步更新对应设计文档
- 新增全局文档 → 同步更新 `docs/INDEX.md`

---

## 三、任务类型决策

开始任何任务前，先判断类别：

| 任务类型 | 是否新开线程 | 是否新建分支 | 分支类型 |
|---|---|---|---|
| 新功能开发 | 必须 | 必须 | `feature/*` |
| Bug 修复 | 必须 | 必须 | `hotfix/*` |
| 文档整理 | 视情况 | 视情况 | 沿用当前分支 |
| 环境配置 | 必须 | 必须 | `feature/*` |

### 必须新开线程的时机

- 任务类型变化（开发 → 修复 → 文档）
- 当前线程跨天且日志过长
- 从"实现"进入"验收反馈修补"

### 禁止混用

- 在功能线程里顺手修无关 bug
- 在 bug 线程里讨论新功能设计
- 在同一线程里连续多轮按截图做 UI 返修

## 四、分支规则

### 起手命令

```bash
cd /Users/lalalaba/Desktop/generate-video
git checkout main
git pull --ff-only origin main
git checkout -b feature/sprint{编号}-{模块名}
```

### 分支生命周期

- `feature/*`：开发完成 → 合并到 `feature/sprint4-stability` → 删除
- `hotfix/*`：修复完成 → 合并到 `feature/sprint4-stability` → 删除
- `feature/sprint4-stability`：当前开发基线，最终合并到 `main`
- `main`：永远存在，只接受 PR 合并

## 五、线程结束交接摘要

> 每次线程结束时输出，下个线程开篇直接粘贴使用。

```text
交接摘要：
1. 背景与目标
2. 当前分支
3. 已修改文件列表
4. 已执行命令与验证结果
5. 是否已提交 / 推送
6. 当前未提交内容
7. 本线程已确认的设计决策
8. 未解决风险 / 待办
9. 下一线程第一步命令
10. 下一线程必读文档
```

如何获取：
```
当前线程结束。
请按交接摘要模板输出完整交接说明，供下个线程直接接手。
```

## 六、文档更新触发条件

以下变化发生后，必须同步更新对应文档：

| 变化 | 需更新的文档 |
|---|---|
| 新增/修改 API | `docs/design/API接口详细设计.md` |
| 数据结构变化 | `docs/design/分镜Schema详细设计.md` |
| 架构决策变化 | `docs/design/平台设计文档.md` |
| 新增全局文档 | `docs/INDEX.md` |
| Sprint 完成 | `docs/operations/planning/开发迭代计划.md` |

**代码、文档、设计三者一致才算任务完成。**

## 七、推荐开场模板

### 新功能开发

```text
目标：开始 Sprint{X} 的 {模块名} 开发。

要求：
- 先确认当前分支、本地 main 与 origin/main 的关系
- 从最新 main 拉新的 feature 分支
- 先给我：功能落点分析、涉及文件、实现路径
- 然后再开始改代码
```

### Bug 修复

```text
目标：只修 {问题描述}，不做新功能。

要求：
- 先定位根因
- 在 hotfix 分支修
- 不要混入无关改动
- 修完给我：根因、改了哪些文件、验证结果
```

### 文档整理

```text
目标：只整理文档，不动代码。

要求：
- 更新后同步检查 docs/INDEX.md 是否需要更新
- 改完告诉我：哪些文档变了、结构是否有变化
```

## 十、主线程（任务管理者）工作流

> 主线程负责制定任务安排、Review 执行线程产出、合并代码、更新计划。
> 不直接执行功能开发，只做 bug 修复和文档更新。

### 10.1 完整工作流

```
计划文档 → 选定任务 → 编写任务安排 → 下发给执行线程 →
执行线程完成 → 输出交接摘要 → 主线程 Review →
核实代码 + 跑测试 → 合并到主干 → 更新计划标记 ✅
```

### 10.2 任务安排模板

每份任务安排必须包含以下结构，缺一不可：

```markdown
## 当前线程：Sprint X.X — 任务名称

=== **背景** ===
为什么需要这个任务，当前存在的问题。

=== **改动范围** ===
| 文件 | 变更 |
|------|------|

=== **技术要点** ===
关键技术决策和实现路径。

=== **验证** ===
- `uv run pytest` 全部通过
- `npm run build` 编译通过
- 手动验证步骤

=== **规范要求** ===
引用的规范章节（§3.1/§8.1 等）。

=== **分支** ===
git checkout feature/sprint4-stability
git checkout -b feature/{分支名}

# 结束时执行（必须）
git add -A
git commit -m "<type>: <描述>"
git push origin {分支名}
```

### 10.3 Review 流程（收到交接摘要后）

**Step 1 — 获取代码**：

```bash
git fetch origin feature/{分支名}
git checkout feature/{分支名}
git diff feature/sprint4-stability --stat
```

**Step 2 — 逐文件核实**：

```bash
# 逐文件查看改动
git diff feature/sprint4-stability -- {文件1}
git diff feature/sprint4-stability -- {文件2}
```

**Step 3 — 检查清单**：

| # | 检查项 |
|---|--------|
| ☐ | 改动文件是否与交接摘要一致 |
| ☐ | 后端 `uv run pytest` 全部通过 |
| ☐ | 前端 `npm run build` 成功 |
| ☐ | 新增字段是否使用 camelCase（§3.6） |
| ☐ | 外部调用是否有降级方案（§8.1） |
| ☐ | 边界条件是否处理（§10） |
| ☐ | 无 API Key / 敏感信息泄露 |

**Step 4 — 合并与更新**：

```bash
git checkout feature/sprint4-stability
git merge feature/{分支名} --no-edit
git push origin feature/sprint4-stability
# 更新开发迭代计划文档标记 ✅
git add docs/operations/planning/开发迭代计划.md
git commit -m "docs: Sprint X.X 标记✅"
git push origin feature/sprint4-stability
```

**Step 5 — 重启服务**（涉及后端/渲染改动时）：

```bash
ps aux | grep uvicorn | grep -v grep | awk '{print $2}' | xargs kill
cd backend && nohup uv run uvicorn app.main:app --host 0.0.0.0 --port 8000 > /dev/null 2>&1 &
```

### 10.4 计划文档维护

每次 Review 合并后立即更新 `开发迭代计划.md`：
- 已完成 → 标记 ✅
- Sprint 整体完成后 → 标记 ✅ 已完成
- 里程碑达成 → 标记 ✅
- 技术债已解决 → 已解决 ✅

### 10.5 分支清理规则

> 分支合并后必须删除，防止残留导致：
> - 本地/远程分支膨胀，干扰 `git branch` 列表
> - 后续线程基于旧分支继续开发产生偏离
> - 同名分支冲突

**单个任务 Review 完成后立即删除**：

```bash
# 合并完成后立即删除源分支
git branch -d feature/{分支名}
git push origin --delete feature/{分支名}
```

**定期批量清理**（每个 Sprint 阶段结束或分支数 > 10 时）：

```bash
# 1. 梳理：列出已合并和未合并分支
git branch --merged feature/sprint4-stability
git branch --no-merged feature/sprint4-stability

# 2. 删除已合并的 feature/hotfix 分支（本地 + 远程）
git branch -d feature/sprintX-xxx feature/sprintX-yyy ...
git push origin --delete feature/sprintX-xxx feature/sprintX-yyy ...

# 3. 如有未合并分支，逐个 Review 决定保留或清理
```

**清理触发条件**：

| 条件 | 操作 |
|------|------|
| 单个 feature 合并到基线后 | 立即删除该分支 |
| Sprint 阶段完成 | 批量清理该阶段所有已合并分支 |
| 本地分支数 > 10 | 执行梳理清理 |
| 发现分支含破坏性变更且代码已手动应用 | 跳过 merge，直接删除分支 |

**保留分支**：
- `main` — 永远保留
- `feature/sprint4-stability` — 当前开发基线
- 未合并且有独立价值的 feature 分支

**禁止**：
- 删除 `main` 或当前基线分支
- 删除未 push 且未合并的分支（`git branch -d` 会拦截，但不要 `-D` 强制删除）
