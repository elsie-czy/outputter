## 二、核心原则（红线）

- `main` 是唯一开发基线
- 新功能必须在 `feature/*` 分支开发
- Bug 修复在 `hotfix/*` 分支修复
- 一个 AI 线程只处理一类任务
- 线程结束必须输出交接摘要
- 代码变更涉及接口/数据结构 → 同步更新对应设计文档
- 新增全局文档 → 同步更新 `docs/INDEX.md`；如影响 V2 计划，再同步更新 `docs/planning/V2_PLAN.md`

## 三、任务类型决策

开始任何任务前，先判断类别：

| 任务类型 | 是否新开线程 | 是否新建分支 | 分支类型 |
|---|---|---|---|
| 新功能开发 | 必须 | 必须 | `feature/*` |
| Bug 修复 | 必须 | 必须 | `hotfix/*` |
| 文档整理 | 视情况 | 视情况 | 沿用当前分支 |
| 环境配置 | 必须 | 必须 | `feature/*` |

### 必须新开线程的时机

- 任务类型变化（开发 → 修复 → 文档）
- 当前线程跨天且日志过长
- 从"实现"进入"验收反馈修补"

### 禁止混用

- 在功能线程里顺手修无关 bug
- 在 bug 线程里讨论新功能设计
- 在同一线程里连续多轮按截图做 UI 返修

## 三点五、Codex 额度与上下文控制

目标：减少长线程、长日志、反复改口径带来的上下文膨胀，让每个线程保持短、准、可交接。

### 3.5.1 核心规则

- 一个线程只做一类事，每个阶段结束后输出交接摘要，再开新线程。
- 大日志不贴全量，只贴关键报错和必要上下文。
- 截图只发关键区域；多状态页面按主状态 / 空状态 / 错误态 / 弹窗分组提供。
- 同类问题一次性打包成 checklist，避免多轮逐条追加。
- UI / 交互 / 文案反馈进入第二轮时，先汇总为本轮问题清单，再开始修改。

### 3.5.2 任务表达规则

- 只需要判断方向时，明确说：`先分析，不要改代码`。
- 已决定执行时，明确说：`直接改`。
- Bug 修复时，明确说：`按 hotfix 流程处理`。
- 新功能开发时，先冻结功能边界、涉及文件、验收标准，再开始实现。

### 3.5.3 字段与页面口径冻结

涉及核心数据、列表页或详情页时，先冻结口径：

- 字段名、含义、是否唯一、是否允许手填、是否自动生成。
- 列表列定义、排序规则、筛选维度。
- 表单录入方式、保存位置、是否写回飞书。
- 页面主任务、默认展示优先级、哪些信息进入高级折叠区。

未冻结前，不进入数据结构、接口或页面实现。

### 3.5.4 强制收口换线程的时机

一个线程内出现以下任意两项时，应收口并开新线程：

- 多轮截图反馈。
- 字段语义或页面口径变化。
- 数据结构新增字段。
- 部署 / 排障开始介入。
- 文档同步开始扩展为独立任务。

超过两次“实现后再改口径”，必须先写口径确认，再继续开发。

### 3.5.5 日志与截图控制

- 日志默认只贴最后 `30~80` 行关键片段。
- 500 / build 失败 / API 错误只贴：报错行、stack、少量上下文。
- 截图开发优先使用 `docs/guides/SCREENSHOT_HANDOFF_TEMPLATE.md`。
- 同一个页面的多张截图应按状态命名，避免混在一起反复解释。

## 四、分支规则

### 起手命令

```bash
cd /Users/lalalaba/Desktop/personal-supertool
git checkout main
git pull --ff-only origin main
git checkout -b feature/{模块名}
```

### 分支生命周期

- `feature/*`：开发 → PR 合并到 `main` → 删除
- `hotfix/*`：修复 → PR 合并到 `main` → 删除
- `main`：永远存在，只接受 PR 合并

## 五、线程结束交接摘要

> 每次线程结束时输出，下个线程开篇直接粘贴使用。

```text
交接摘要：
1. 背景与目标
2. 当前分支
3. 已修改文件列表
4. 已执行命令与验证结果
5. 是否已提交 / 推送
6. 当前未提交内容
7. 本线程已确认的设计决策
8. 未解决风险 / 待办
9. 下一线程第一步命令
10. 下一线程必读文档
```

## 七、推荐开场模板

### 新功能开发

```text
目标：开始 {模块名} 开发。

要求：
- 从 main 拉新的 feature 分支
- 先给我：功能落点分析、涉及文件、实现路径
- 然后再开始改代码
- 遵循 docs/guides/开发规范手册.md 代码规范
```

### Bug 修复

```text
目标：只修 {问题描述}，不做新功能。

要求：
- 先定位根因
- 在 hotfix 分支修
- 不要混入无关改动
- 修完给我：根因、改了哪些文件、验证结果
```

### 文档整理

```text
目标：只整理文档，不动代码。

要求：
- 改完告诉我：哪些文档变了、结构是否有变化
```

### 截图/设计图开发

```text
目标：按截图实现 {页面/组件名称}。

要求：
- 先阅读 docs/guides/SCREENSHOT_HANDOFF_TEMPLATE.md 和 docs/guides/ui-rules.md
- 先拆解截图：布局、组件、状态、接口、涉及文件
- 再开始改代码
- 不往 scripts/web_app_legacy.py 增加新逻辑
- 完成后启动服务并用浏览器验收
```

## 八、文件长度与复杂度控制

| 文件类型 | 最大行数 | 超限后 |
|---|---|---|
| Python 模块 | 500 行 | 拆分子模块 |
| Jinja2 模板 | 300 行 | 抽取 `_components/` 宏 |
| JS 文件 | 300 行 | 按功能拆文件 |
| 设计文档 | 不限 | 但章节不宜超过 10 个 |

提交信息格式：`feat: / fix: / docs: / refactor: / chore:` + 简短描述

## 九、Code Review 检查清单

> 每次功能开发线程结束、合并到 main 前，必须逐项确认。

| # | 检查项 |
|---|---|
| ☐ | 改动文件是否与交接摘要一致 |
| ☐ | 服务可正常启动（`python scripts/web_app.py` 无报错） |
| ☐ | 新页面/API 可通过 curl 或浏览器验证 |
| ☐ | 模板文件使用 Jinja2 `{% extends %}` / `{% include %}` 正确 |
| ☐ | CSS 复用 `var(--color-*)` 等变量，不硬编码颜色值 |
| ☐ | 无 API Key / 敏感信息硬编码 |
| ☐ | 外部 API 调用有 try-except 和超时 |
| ☐ | 边界条件已处理（空列表、None 值、文件不存在） |
| ☐ | 新增文件遵循命名规范（snake_case） |
| ☐ | 相关设计文档已同步更新 |

## 十、主线程（任务管理者）工作流

> 主线程负责制定任务安排、Review 执行线程产出、合并代码、更新计划。
> 不直接执行功能开发，只做 bug 修复和文档更新。

### 10.1 完整工作流

```
计划文档 → 选定任务 → 编写任务安排 → 下发给执行线程 →
执行线程完成 → 输出交接摘要 → 主线程 Review →
核实代码 + 验证 → 合并到 main → 更新计划标记 ☑
```

### 10.2 任务安排模板

```markdown
## 当前线程：Sprint V2.X — 任务名称

=== **背景** ===
...

=== **改动范围** ===
| 文件 | 变更 |
|------|------|

=== **技术要点** ===
...

=== **验证** ===
...

=== **规范要求** ===
...

=== **分支** ===
git checkout main
git checkout -b feature/{分支名}

# 结束时执行（必须）
git add -A
git commit -m "<type>: <描述>"
git push origin {分支名}
```

### 10.3 Review 流程（收到交接摘要后）

**Step 1 — 获取代码**：
```bash
git fetch origin feature/{分支名}
git checkout feature/{分支名}
git diff main --stat
```

**Step 2 — 逐文件核实**：
```bash
git diff main -- {文件1}
git diff main -- {文件2}
```

**Step 3 — 检查清单**：按 §九 逐项验证

**Step 4 — 合并与更新**：
```bash
git checkout main
git merge feature/{分支名} --no-edit
git push origin main
# 更新 V2_PLAN.md 任务标记 ☑
git add docs/planning/V2_PLAN.md
git commit -m "docs: 任务 X.X 标记 ☑"
git push origin main
```

**Step 5 — 重启服务**（涉及后端改动时）：
```bash
# 停止旧进程
ps aux | grep web_app | grep -v grep | awk '{print $2}' | xargs kill
# 启动
cd /Users/lalalaba/Desktop/personal-supertool
source .venv/bin/activate
nohup python scripts/web_app.py > /dev/null 2>&1 &
```

### 10.4 计划文档维护

每次 Review 合并后立即更新 `docs/planning/V2_PLAN.md`：
- 已完成任务 → 标记 ☑
- 进度总览百分比同步更新

### 10.5 分支清理规则

合并后必须删除源分支：

```bash
git branch -d feature/{分支名}
git push origin --delete feature/{分支名}
```

## 十一、与 generate-video 原版规范的差异

本规范从 generate-video 项目适配，删除了以下不适用的内容：

- `feature/sprint4-stability` 基线分支（本项目直接用 `main` 为基线）
- uvicorn/FastAPI 服务重启命令（本项目用 Flask）
- `uv run pytest` / `npm run build` 验证（本项目用 Flask 启动 + curl 验证）
- camelCase 字段命名规则（本项目无 Pydantic/TypeScript）
- 云端发布、生产排障规则（暂无部署环境）
- CODEX 原版规范引用
